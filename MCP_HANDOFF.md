# MCP_HANDOFF.md — Implementation Handoff: Connect GATE AI Tracker to ChatGPT via MCP

Read `MCP_AUDIT.md` first — this document assumes it and doesn't repeat the full reasoning, only the actionable instructions. **Nothing in this repository has been modified. This is a plan, not a diff.**

---

## 1. Current architecture (as-is)

```
Browser
  ↓ HTTP-only cookie (gate_ai_session)
Next.js 14 App Router, deployed on Vercel
  ↓ getCurrentUser() reads Session table
  ↓ Prisma Client
Neon PostgreSQL
```

- Single-user personal app. One `User` row, created by `prisma/seed.ts`.
- Every `/api/*` route re-checks auth itself via `getCurrentUser()`/session cookie; `middleware.ts` only does a cheap Edge-level cookie-presence check (it cannot query Postgres from the Edge runtime).
- A separate, unrelated AI feature ("Luna", Optimizer → Bedrock) already exists at `/api/chat` — leave it untouched (Section 13).
- No MCP code, no OpenAI key, no OAuth server exist anywhere today.

## 2. Target architecture (to build)

```
ChatGPT (MCP client)
   ↓ HTTPS, Authorization: Bearer <mcp-token>
Custom MCP server  ── new Next.js API route(s), e.g. app/api/mcp/route.ts, deployed
                       on the SAME Vercel project/deployment as the website
   ↓ identity resolved via new McpApiToken lookup (NOT the cookie session)
   ↓ same Prisma calls, same userId-scoping pattern as existing REST routes
Existing tracker backend (lib/db/*, lib/validation/schemas.ts — reused, not duplicated)
   ↓ Prisma
Neon PostgreSQL (same database, no new instance)
```

Hard constraints from the user, restated so they aren't lost in implementation:
- The main website **must stay on Vercel**. Do not propose moving anything to AWS/Lambda/EC2/etc. The MCP server should be **additional API route(s) inside this same Next.js app**, not a separate service, unless a genuine technical blocker (see Section 11) forces otherwise — and if so, stop and ask the user before doing it.
- **No OpenAI API key goes into this project.** The tracker itself never calls OpenAI. ChatGPT is the *client* connecting outward to the MCP server; the MCP server does not need to call any LLM API to serve tool calls (its job is to read/write Postgres via Prisma, not to generate text). If future work wants the tracker to call OpenAI directly for something else, that's a separate decision the user hasn't asked for here — don't bundle it in.

## 6. Authentication recommendation

Implement **Option A from MCP_AUDIT.md Section 5a: a hashed, revocable API token**, not full OAuth, unless the user explicitly asks for OAuth after reading the tradeoffs. Concretely:

1. New Prisma model:
   ```prisma
   model McpApiToken {
     id         String    @id @default(cuid())
     userId     String
     user       User      @relation(fields: [userId], references: [id], onDelete: Cascade)
     name       String
     tokenHash  String    @unique
     lastUsedAt DateTime?
     revokedAt  DateTime?
     createdAt  DateTime  @default(now())

     @@index([userId])
   }
   ```
   Add the back-relation `mcpApiTokens McpApiToken[]` to `User`.
2. Token = `crypto.randomBytes(32).toString("hex")` (or similar), shown to the user exactly once at creation time; store only `sha256(token)` in `tokenHash`.
3. MCP route reads `Authorization: Bearer <token>`, hashes it, looks up `McpApiToken` where `tokenHash` matches and `revokedAt IS NULL`, resolves `userId`, updates `lastUsedAt`, and proceeds — mirroring `getCurrentUser()`'s shape so every downstream Prisma call is unchanged.
4. Every MCP tool handler must still do the same `userId`-scoped queries and `findFirst` ownership checks as the REST routes — the token only replaces *how identity is established*, not the authorization model underneath it.

## 7. Security requirements (non-negotiable)

- Store only a hash of the MCP token, never the raw value (same principle as `User.passwordHash`).
- Serve the MCP endpoint over HTTPS only (Vercel default — don't disable).
- Never log the raw token or the `Authorization` header in any `console.log`/`console.error` call.
- Keep every existing per-row `userId` ownership check in every tool handler — do not introduce a shortcut that queries by `id` alone.
- Add basic rate limiting to the new MCP endpoint (it doesn't exist anywhere else in the app either, but a new externally-reachable write surface is a good place to finally add it — e.g. a simple DB-backed or Upstash-backed limiter). Flag to the user if this is deferred.
- Do not expose a raw "write to DailyProgress" tool (it's a derived table — writes must go through StudyTask/StudySession paths, per audit Section 3/7).
- Add the token-revocation path (`revokedAt`) before shipping, even if there's no UI for it yet (a one-off script/Prisma Studio edit is acceptable for v1, but the column and the check in `getUserFromMcpToken` must exist).

## 9. Testing requirements

Before considering this done:
1. **Unit/integration**: for each new MCP write tool, verify (a) the correct Prisma rows are created/updated, (b) `DailyProgress` counters are correctly adjusted where applicable, (c) cross-user ownership is enforced (attempt to reference another user's `subjectId`/`topicId`/`questionId` and confirm rejection, matching existing REST route behavior).
2. **Auth tests**: valid token succeeds; missing token 401s; revoked token 401s; expired/malformed token 401s; token for user A cannot read/write user A's data via a spoofed `userId` in the request body (the tool handler must always derive `userId` from the resolved token, never trust a client-supplied `userId`).
3. **Regression**: confirm the existing cookie-based web app still works unmodified — log in, view dashboard, create/edit a study task, stop a study timer, and confirm `DailyProgress`/streak numbers update exactly as before your changes (audit Section 9, biggest regression risk).
4. **Date fix verification**: after applying the `2027-02-07` fixes (Section 3), confirm `npx prisma migrate dev` runs cleanly and a fresh `UserSettings` row gets the corrected default; confirm the dashboard's "Days Remaining" is unchanged (it already used the correct code-level constant, so this should be a no-op for existing users, but must be verified for new ones).
5. **Manual MCP client test**: connect an actual MCP client (ChatGPT's connector, or `mcp-inspector`/similar) against the deployed Vercel preview URL and exercise every read and write tool end-to-end before connecting the production ChatGPT account.
6. Run the existing pre-deploy checklist from `README.md` Section 6 (`npx prisma validate`, `npx prisma generate`, `npx tsc --noEmit`, `npm run lint`, `npm run build`) — none of it was run as part of this audit, so it must be run fresh after implementation.

## 11. Architectural risks / open questions to confirm with the user before/while implementing

1. **`record_study_session` shape** (single "log completed session" call vs. mirroring start/stop) — ask the user which fits how they'll actually talk to ChatGPT about study sessions.
2. **Token issuance UX** — does the user want a `/settings` UI panel to mint/revoke MCP tokens, or is a one-off authenticated script/manual DB insert acceptable for a single-user app? This affects how much new UI work is in scope.
3. **Live Vercel env vars** — confirm whether `TARGET_EXAM_DATE` is explicitly set (and wrong) in the actual Vercel project settings; this repo audit cannot see that.
4. **Rate limiting** — currently absent app-wide; decide whether to add it just for the new MCP surface (recommended, minimal effort with a DB counter) or treat it as a known gap to fix later.
5. **OAuth vs. token** — Option A (token) is recommended, but if the user anticipates ever exposing this to more than themselves, flag that OAuth would be the more future-proof (but much larger) investment, and confirm they're fine with Option A for now.
6. Confirm whether the `2027-02-25` → `2027-02-07` fixes should ship in the **same** PR/deploy as the MCP work, or as a separate, smaller, immediate fix — they're unrelated to MCP and could be shipped independently and sooner.

## 12. Existing bugs that must not regress

See MCP_AUDIT.md Section 9 in full. The one that actually matters for this project: **any new write path (MCP or otherwise) that creates/updates/deletes a `StudyTask` or stops a `StudySession` must call `adjustTaskCounts`/`addStudySeconds` exactly as the existing REST routes do**, or the dashboard's streaks and task counts will silently drift from reality. This is the single highest-risk regression in the whole task.
